# قرارداد API پنل مرکزی ← کافینو: اطلاعیه و تیکت (نسخهٔ ۱.۶۲)

کافینو خودش به پنل مرکزی وصل می‌شود (همان `apiBaseUrl` و `cafeId` در `config.js`) و با توکن ورود کاربر درخواست می‌زند.
پنل مرکزی **باید** این مسیرها را پیاده کند؛ اگر نباشند (۴۰۴/۴۰۵/۵۰۱) برنامه خطا نمی‌دهد و فقط «پشتیبانی نمی‌شود» نشان می‌دهد.
پاسخ‌ها هم به شکل `{ "data": … }` و هم آرایهٔ خام پذیرفته می‌شود. خطاها: `{ "error": { "code", "message" } }`.

سرور مرجع (فقط توسعه/تست، بدون بررسی توکن): `node admin-reference/server.mjs` — همین قرارداد را اجرا می‌کند.

## هدرهای هر درخواست
`Authorization: Bearer …`، `X-Cafe-Id`، `X-Organization-Id` و `X-Branch-Id` (در صورت وجود).
**این هدرها فقط راهنمای مسیریابی‌اند.** پنل باید از روی توکن تشخیص دهد کاربر به کدام کافی‌نت تعلق دارد و هر کافی‌نت فقط
اطلاعیه‌های مخصوص خود/همگانی و تیکت‌های خودش را ببیند.

## اطلاعیه‌ها (فقط‌خواندنی)
`GET /api/announcements?limit=100`
```json
{ "data": [ {
  "id": "a_1", "title": "عنوان", "body": "متن (متن ساده، چندخطی)",
  "severity": "info | warning | critical",   // critical = نوار قرمز بالای برنامه تا کاربر «خواندم» بزند
  "pinned": false, "publishedAt": "2026-10-31T10:00:00Z",
  "expiresAt": "",                           // اختیاری؛ بعد از آن نمایش داده نمی‌شود
  "link": "https://…"                        // اختیاری، فقط http(s)
} ] }
```
• «خوانده‌شدن» فقط در همان دستگاه نگه‌داری می‌شود؛ مسیر تأیید خواندن لازم نیست.
• پنل می‌تواند اطلاعیه را برای همهٔ کافی‌نت‌ها یا فقط تعدادی بفرستد؛ فیلتر سمت پنل است.

## تیکت‌ها
`GET /api/tickets?limit=100` ← فهرست تیکت‌های همین کافی‌نت، هرکدام با `messages`
```json
{ "data": [ {
  "id": "tk_…", "number": "1001", "subject": "…", "category": "technical|billing|feature|other",
  "priority": "low|normal|high", "status": "open|pending|answered|closed",
  "createdAt": "…", "updatedAt": "…",
  "messages": [ { "id": "m_…", "from": "cafe|admin", "author": "نام", "body": "…", "createdAt": "…" } ]
} ] }
```
`from: "admin"` یعنی پاسخ پشتیبانی؛ پاسخ جدید ادمین (با `createdAt` بعد از آخرین بازدید) روی دستگاه «نخوانده» نشان داده می‌شود.
برای کاربر سمت پنل، وضعیت پیشنهادی بعد از پاسخ ادمین `answered` است.

`POST /api/tickets` ← ساخت تیکت. **شناسهٔ `id` را کلاینت می‌سازد و سرور باید همان را نگه دارد.**
هدر `Idempotency-Key: tickets-<id>` ارسال می‌شود؛ ارسال تکراری باید همان تیکت را (۲۰۰) برگرداند، نه تیکت دوم.
```json
{ "id": "tk_…", "subject": "…", "category": "technical", "priority": "normal", "status": "open",
  "createdAt": "…", "body": "متن",
  "message": { "id": "m_…", "body": "متن", "createdAt": "…", "author": "نام کاربر" },
  "source": { "app": "cafino", "version": "1.62.0" } }
```
پاسخ: تیکت کامل (۲۰۱) با `number`.

`POST /api/tickets/:id/messages` ← پاسخ کافی‌نت. `Idempotency-Key: ticket-message-<id>`؛ بدنه `{ id, body, createdAt, author }`.
اگر تیکت بسته است ۴۰۹ بدهید (برنامه جلوی این حالت را هم می‌گیرد). پاسخ کافی‌نت به تیکتِ `answered` آن را `open` می‌کند.

`PATCH /api/tickets/:id` ← `{ "status": "closed" }` یا `{ "status": "open" }` (بستن / بازکردن دوباره توسط کافی‌نت).

## نکات پیاده‌سازی
• همهٔ ارسال‌ها از «صف آفلاین» می‌روند: ممکن است دیر برسند، تکراری تلاش شوند، یا پاسخ گم شود؛ پس Idempotency الزامی است.
• پیام‌ها نباید ویرایش/حذف شوند (برنامه آن‌ها را با `id` ادغام می‌کند). حذف کامل تیکت از فهرست = حذف از دستگاه.
• دریافت هر ۶۰ ثانیه (فقط وقتی برنامه باز و دیدنی است)، هنگام برگشت اینترنت و هنگام برگشتن به برنامه انجام می‌شود. اعلان لحظه‌ای وقتی برنامه بسته است در این نسخه پشتیبانی نمی‌شود
  (push-server فعلی فقط یادآورهای زمان‌بندی‌شدهٔ خود کاربر را می‌فرستد)؛ اگر برنامه در پس‌زمینه ولی باز باشد و مجوز اعلان داده شده باشد، اعلان سیستم‌عامل نشان داده می‌شود.
• محدودیت‌ها: عنوان ۲۰۰ و متن ۸۰۰۰ نویسه؛ تا ۱۰۰ اطلاعیه و ۲۰۰ تیکت روی هر دستگاه نگه‌داری می‌شود (`limit` را بیشتر از ۱۰۰ فرض نکنید).
• حالت مهمان هرگز به سرور وصل نمی‌شود و دادهٔ نمونه نشان می‌دهد.
