# کافینو — سرور (API + پایگاه‌داده) — راهنمای استقرار

پشته: **Node.js ≥ 22.12 + Fastify 5 + PostgreSQL ≥ 14** (آزمون‌ها روی PostgreSQL 16 هم اجرا شده‌اند؛ ایمیج compose همان 16 است). برنامهٔ کافینو (PWA/دسکتاپ) همچنان «اول محلی» کار می‌کند؛ این سرور
همگام‌سازی چنددستگاهی، پنل مرکزی (کافی‌نت‌ها، اطلاعیه و تیکت)، گزارش‌های SQL و حسابرسی سمت سرور را فراهم می‌کند.

```
مرورگر/PWA/دسکتاپ ──HTTPS──► nginx (فایل‌های برنامه + /api) ──► API (Fastify) ──► PostgreSQL
        └─ صف آفلاین (IndexedDB)  ↺ Idempotency-Key            └─ لاگ حسابرسی با زنجیرهٔ هش
```

## ۱) راه‌اندازی سریع با Docker
> راهنمای کامل Ubuntu (Docker، HTTPS، فایروال، پشتیبان/بازیابی، مانیتورینگ، چرخش لاگ): **`DEPLOY-UBUNTU-fa.md`**
```bash
# ریشهٔ مخزن: خروجی تأییدشده (dist/pwa + dist/manifest.json) را بسازید
npm ci && npm run build && npm run verify:dist
cd server
cp .env.example .env            # JWT_SECRET (openssl rand -hex 48)، POSTGRES_PASSWORD و APP_DB_PASSWORD (openssl rand -hex 24) را پر کنید
node deploy/make-csp.mjs ../dist/pwa   # CSP با هش اسکریپت‌های برنامه (بعد از هر بیلد تکرار شود)
docker compose up -d --build    # پایگاه‌داده + API + nginx روی 127.0.0.1:8080 (TLS را پراکسی جلویی می‌دهد)
docker compose exec api node scripts/create-admin.mjs admin@example.com 'یک-رمز-طولانی-و-قوی'
```
`config.js` این استقرار در `deploy/config.js` است (same-origin) و روی فایل داخل `dist/pwa` سوار می‌شود؛ پس `dist/` دست‌نخورده و هش‌هایش معتبر می‌ماند.
بدون Docker: پایگاه‌داده را بسازید، `DATABASE_URL` و `JWT_SECRET` را در محیط بگذارید، `npm ci --omit=dev && npm start` (Node ≥ 22.12)
(مهاجرت‌ها هنگام شروع خودکار اجرا می‌شوند؛ `AUTO_MIGRATE=false` یا `npm run migrate` برای اجرای جدا).

## ۲) HTTPS و دامنه
nginx داخل بسته روی HTTP است؛ جلوی آن یک پروکسی TLS بگذارید. نمونهٔ Caddy:
```
cafino.example.com {
  reverse_proxy 127.0.0.1:8080
}
```
با HTTPS، `COOKIE_SECURE=true` و `TRUST_PROXY=1` (پیش‌فرض تولید) بمانند. HSTS را Caddy/nginx میزبان اضافه می‌کند.

### IP واقعی کاربر و Trust Proxy (از ۱.۷۱.۰)
IP کاربر برای **محدودکنندهٔ نرخ، قفل ورود و لاگ حسابرسی** استفاده می‌شود؛ پس نباید با هدر جعلی `X-Forwarded-For` قابل تعیین باشد.
- nginx داخل بسته هدر کاربر را **بازنویسی** می‌کند (`X-Forwarded-For $remote_addr`، `X-Real-IP $remote_addr`)، نه اینکه به آن اضافه کند.
- اگر nginx مستقیماً به اینترنت وصل است، کاری لازم نیست: هر `X-Forwarded-For` ارسالی کاربر نادیده گرفته می‌شود.
- اگر جلوی آن Caddy/nginx میزبان/load balancer هست، **فقط آدرس همان پراکسی** را در `deploy/trusted-proxies.conf` بنویسید
  (`set_real_ip_from 172.16.0.0/12;`) و `docker compose exec web nginx -s reload` بزنید. IP واقعی از X-Forwarded-For پراکسی خوانده می‌شود، نه از هر کسی.
- `TRUST_PROXY` در API: خالی/`1`/`true` = یک هاپ (nginx)، عدد N = N پراکسی، `false` = بدون پراکسی، یا فهرست `172.16.0.0/12,10.0.0.0/8`.
  «اعتماد به همه» وجود ندارد و `*` خطای پیکربندی است. API نباید مستقیماً از اینترنت در دسترس باشد (در docker-compose فقط روی شبکهٔ internal است).

## ۳) اولین استفاده
1. مدیر پنل مرکزی را با `create-admin` بسازید (بالا).
2. با `POST /api/auth/login` وارد شوید و کافی‌نت بسازید: `POST /api/admin/cafes` ← مالک و **رمز موقت یک‌بارمصرف** برمی‌گردد
   (کاربر در اولین ورود مجبور به تغییر رمز است). ثبت‌نام عمومی در تولید بسته است (`ALLOW_REGISTRATION=false`).
   ورود: بعد از ۳ رمز اشتباه (همان IP یا همان ایمیل، ۱۵ دقیقه) کپچای عددی ۵ رقمی که خود سرور می‌سازد (بدون سرویس بیرونی) خواسته می‌شود؛ `CAPTCHA_AFTER_FAILS` (۰ = خاموش) و `CAPTCHA_WINDOW_MIN`. قفل حساب بعد از ۸ رمز اشتباه مستقل از آن است.
   **پیامک (ملی پیامک، ۱.۸۸):** با تنظیم `MELIPAYAMAK_USERNAME`/`MELIPAYAMAK_PASSWORD` و (`MELIPAYAMAK_OTP_BODY_ID` یا `MELIPAYAMAK_FROM`) در `.env`، صفحهٔ ورود «ورود با کد پیامکی» و ثبت‌نام «تأیید شماره با کد» پیدا می‌کند (`GET /api/auth/sms/config` وضعیت را می‌گوید). بدون این متغیرها همه‌چیز مثل قبل است. ارسال پیامک به مشتریان جداست: هر کافی‌نت پنل خودش را در «تنظیمات ← اتصال ← پیامک» وصل می‌کند (رمز با AES-256-GCM رمزنگاری می‌شود) و دسترسی‌های `sms.send`/`sms.manage` را مالک به کارمندان می‌دهد.
3. مالک کافی‌نت در برنامه وارد می‌شود. اگر داده‌ای از قبل روی آن دستگاه دارد:
   **تنظیمات ← همگام‌سازی ← «ارسال دادهٔ موجود به سرور»** (امن و تکرارپذیر است؛ ارسال دوباره رکورد دوم نمی‌سازد).
4. اطلاعیه و پاسخ تیکت: با توکن مدیر به `/api/admin/…` (فهرست کامل در `openapi.yaml`).

## ۴) config.js برنامه
`apiBaseUrl: "same-origin"` وقتی برنامه و API پشت یک دامنه‌اند (پیشنهادی؛ کوکی و CORS ساده می‌ماند).
دامنهٔ جدا: `apiBaseUrl: "https://api.example.com"` و در سرور `CORS_ORIGINS=https://app.example.com` (کوکی `SameSite=None; Secure` خودکار می‌شود).

## ۵) پایگاه‌داده
- طرح در `migrations/*.sql` (فقط افزودنی؛ مهاجرت‌های اجراشده هرگز تغییر نمی‌کنند، تغییر جدید = فایل جدید).
- هر کافی‌نت مستأجر جداست: کلید اصلی `(cafe_id, id)`؛ هر پرس‌وجو با `cafe_id` توکن فیلتر می‌شود (هدر `X-Cafe-Id` فقط راهنماست).
- مبلغ‌ها عدد صحیح (ریال)؛ حذف نرم (`deleted_at`)؛ فیلدهای برنامه که ستون ندارند در `data jsonb` می‌مانند.
- پشتیبان: `deploy/backup.sh` (روزانه، ۱۴ روز، با بررسی صحت و SHA-256) و `deploy/restore.sh` (تمرین بازیابی روی پایگاه‌دادهٔ موقت یا جایگزینی تولید) — **یک نسخه را بیرون از سرور نگه دارید** (`OFFSITE_CMD`) و بازیابی را یک بار تمرین کنید.
- لاگ حسابرسی: `GET /api/audit/verify` سالم‌بودن زنجیرهٔ هش را می‌سنجد (دستکاری مستقیم ردیف‌ها لو می‌رود).

### TLS پایگاه‌داده (از ۱.۷۱.۰)
- PostgreSQL داخل شبکهٔ docker همین بسته: `DB_SSL=false` درست و کافی است (پایگاه‌داده بیرون منتشر نمی‌شود).
- پایگاه‌دادهٔ جدا/ابری: `DB_SSL=true` ← گواهی و نام میزبان **همیشه تأیید می‌شود** (`rejectUnauthorized: true`). اگر CA خصوصی دارید فایل را در `server/certs/ca.pem` بگذارید و `DB_SSL_CA_FILE=/certs/ca.pem` را بنویسید (یا PEM را در `DB_SSL_CA` با `\n`).
- ⚠️ تغییر رفتار: پیش از این `DB_SSL=true` گواهی را تأیید نمی‌کرد. اگر پایگاه‌دادهٔ شما گواهی خودامضا دارد و CA را نمی‌دهید اتصال رد می‌شود؛ CA را بدهید.
- `DB_SSL=no-verify` فقط برای آزمایش است و در تولید بدون `DB_SSL_ALLOW_INSECURE=true` سرور بالا نمی‌آید. `sslmode` را داخل `DATABASE_URL` نگذارید.
- اگر در تولید میزبان پایگاه‌داده عمومی به‌نظر برسد ولی TLS خاموش باشد، هنگام شروع هشدار در لاگ نوشته می‌شود.

### نشست آفلاین (از ۱.۷۱.۰)
`OFFLINE_SESSION_MAX_AGE_OWNER_SEC` (پیش‌فرض ۲۴ ساعت) و `OFFLINE_SESSION_MAX_AGE_STAFF_SEC` (پیش‌فرض ۸ ساعت) را سرور در `offlinePolicy` کاربر به برنامه می‌دهد؛
پس از آن مدت، برنامه بدون ورود آنلاین کار نمی‌کند. عملیات حساس مالی (ابطال، تعدیل، برگشت وجه، حذف…) آفلاین مجاز نیست.

## ۸) محدودیت‌ها و تصمیم‌های آگاهانه
- **شمارهٔ فاکتور** را هر دستگاه آفلاین می‌سازد؛ یکتایی سخت صف همگام‌سازی را قفل می‌کرد. تکراری‌ها در `/api/reports/summary` گزارش می‌شوند.
- **وضعیت/مانده/پرداخت‌شده‌ٔ فاکتور** را سرور از مبالغ و پرداخت‌ها می‌سازد؛ مقدار کلاینت نادیده گرفته می‌شود. بین رسیدن فاکتور و پرداخت‌هایش ممکن است لحظه‌ای مانده موقت باشد (ثبت نهایی سازگار).
- **موجودی کالا** = موجودی اولیه + مجموع حرکت‌ها و **کیف پول مشتری** فقط هنگام ساخت از کلاینت پذیرفته می‌شود؛ PATCH آن‌ها را عوض نمی‌کند (بخش ۹).
- تعارض هم‌زمان دو دستگاه روی یک رکورد: «آخرین نوشتن برنده» (`updated_at`)؛ فیلدهای مالی بالا به‌صورت جمع/حرکت امن‌اند.
- اعلان لحظه‌ای وقتی برنامه بسته است هنوز از `push-server` جداست؛ اطلاعیه‌ها هنگام باز بودن برنامه هر ۶۰ ثانیه دریافت می‌شوند.
- یک نمونهٔ API کافی است؛ برای چند نمونه کافی است پشت load balancer بگذارید (Idempotency و قفل‌ها در PostgreSQL‌اند، نه حافظه). محدودیت نرخ فعلاً درون‌حافظه‌ای و برای هر نمونه است.

## ۹) یکپارچگی مالی (از نسخهٔ ۱.۶۶.۰)
قاعدهٔ کلی: **هر مبلغِ مشتق را فقط سرور می‌سازد؛ کلاینت فقط «رویداد» می‌فرستد (قلم فاکتور، پرداخت، حرکت انبار، تعدیل).**

| موضوع | قاعده |
|---|---|
| فاکتور | کلاینت `items`، `discount`، `waivedAmount` و اطلاعات توصیفی می‌فرستد. `subtotal` = Σ(تعداد×قیمت قلم‌ها)، `totalAmount` = subtotal − discount، `paidAmount` = Σ پرداخت‌ها − برگشت‌ها، `remainingAmount` و `status` مشتق‌اند. فیلدهای `subtotal/totalAmount/paidAmount/remainingAmount/status` در ورودی **نادیده** گرفته می‌شوند (رد نمی‌شوند تا صف آفلاین نسخه‌های قدیمی گیر نکند). ابطال فقط با `POST /api/invoices/:id/void {reason}` (مدیر). فاکتور بدون قلم رد می‌شود (`422`) مگر مدیر `totalAmount` دستی بدهد (فاکتور بازمانده/دستی). |
| پرداخت | **حذف ندارد** (`DELETE` ← ۴۰۵؛ تریگر پایگاه‌داده هم حتی با SQL مستقیم جلوی حذف/تغییر مبلغ را می‌گیرد). اشتباه = `POST /api/payments/:id/void {reason}` که ردیف «برگشت» با مبلغ منفی می‌سازد؛ هر پرداخت فقط یک بار برگشت می‌خورد. برگشت برای مالک/مدیر/کارمند مجاز است (کلاینت هنگام ویرایش فاکتور پرداخت‌های قدیمی را برگشت می‌زند) ولی `reason` الزامی و در حسابرسی است؛ برای محدودکردن به مدیر `PAYMENT_VOID_ROLES` را عوض کنید. ویرایش (`PATCH`) فقط مدیر، فقط فیلدهای غیرمالی (روش/تاریخ/حساب) و با `reason`. |
| حساب (`accounts`) | `balance` را کلاینت عوض نمی‌کند. مانده = Σ ردیف‌های `ledger_entries` (مانده اولیه + فاکتور − پرداخت + تعدیل − برگشت وجه؛ بدهکار مثبت). ردیف‌ها تغییرناپذیرند (تریگر). تعدیل: `POST /api/accounts/:id/adjust {amount|kind, reason}` (مدیر)؛ دفتر: `GET /api/accounts/:id/ledger`. |
| انبار | `qty` = `opening_qty` + Σ حرکت‌ها. بازسازی: `POST /api/inventory/rebuild {itemId?, dryRun?, reason?}`؛ دفتر کالا: `GET /api/inventory/:id/ledger`. |
| ارجاع‌ها (FK هم‌مستأجر) | کلید خارجی ساده صف آفلاین را می‌شکند، پس ارجاع به مشتری/فاکتور در **لحظهٔ نوشتن** بررسی می‌شود (`422 unknown_reference`)؛ کلاینت با `dependsOn` ترتیب را رعایت می‌کند. برای ورود داده‌های قدیمی `REFERENCE_CHECKS=off`. کلیدهای خارجی واقعی: برگشت‌پرداخت→پرداخت، حرکت انبار→کالا، ردیف دفتر→حساب. |
| حسابرسی | `invoice.create/update/void`، `payment.create/update/void`، `expense.*`، `transaction.*`، `account.adjust`، `inventory.movement`، `*.delete`، `integrity.rebuild` با `before/after`، کاربر، زمان، IP و `reason` در زنجیرهٔ هش ثبت می‌شود. |
| بازرسی | `GET /api/integrity` (مدیر): یتیم‌ها + انحراف مقادیر مشتق؛ `POST /api/integrity/rebuild {scope:["invoices","accounts","inventory"], dryRun?, reason?}`: بازسازی از منبع حقیقت. |

**بخشودگی (`waivedAmount`)**: کلاینت «پرداخت رایگان» را همگام نمی‌کند و فقط مقدار بخشودگی فاکتور را می‌فرستد؛ سرور آن را به [۰، مبلغ] محدود می‌کند، در دفتر حساب ردیف تعدیل می‌گذارد و در حسابرسی ثبت می‌کند. این هنوز توسط کارمند هم قابل ثبت است (مثل برنامه)؛ برای سخت‌تر کردن، نقش را در `prepareInvoice` به مدیر محدود کنید.
